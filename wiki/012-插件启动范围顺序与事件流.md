## 先说结论

| 问题 | 一句话 |
|---|---|
| 是否所有插件都启动？ | **否**。只挂 composed entry 列表；preset 的 `agent.cordis.yml` 更晚、按会话 |
| 启动先后顺序？ | **YAML 行序 ≠ 启动序**；同层并发，按 `inject` / 服务可用性激活 |
| 是否全靠事件？ | **否**。主干是**服务方法调用**；事件做拦截、策略、广播 |
| 事件流程？ | 分 **Session 事件**（落盘）与 **Cordis 事件**（进程内）；一次说话走 RPC → `followup` → turn/step |

```text
叠 patch（只组配置）
  → prepare（cmdlineArgs / appReady…）
  → Loader 并发 mount（inject 决定谁先活）
  → appReady
  ── 之后，首个会话 ──
  mount preset（Agent 平面）
  ── 用户说话 ──
  Remote prompt → agent.followup → turn/step
    ↔ waterfall（pre-step / llm/stream / tools/*）
    → Session 日志 → session/event → UI
```

## 1. 启动后是否所有插件都需要启动？

**否。** `packages/` 里约 255 个包是货架；进程里只挂 **当前 profile 叠完 patch 之后** 的那些行。

```text
空 entry 列表
  → bundle 1…n（如 web: dsh-base → dsh-web-app）
  → profiles/<name>/cordis.patch.yml
  → $DSH_HOME/cordis.patch.yml
  → --patch
```

| 范围 | 会不会挂 |
|---|---|
| 仓库全部 `@deepseek-ai/dsh-*` | 不会 |
| `dsh-base` 约 85 行 + mode bundle + 用户 patch | 会（**Host 平面**） |
| `disabled: true` 的行（如 HMR、按平台关掉的 bash/pwsh） | 不激活 |
| 某 preset 的 `agent.cordis.yml` | Host boot **不挂**；首个会话 create/resume 才 `ensureStanding` |

Host 启动只挂 `agent-presets` 的 **roster**（扫目录、建名单）；真正把 `standard` / `ptc` 等 Agent 平面插件 Include 进来，要等会话选用 preset（见 [006](./006-四种Agent-Presets对比.md)、[009](./009-cordis.patch与agent.cordis的区别.md)）。

本机核对叠完后的树（不是扫 `packages/`）：

```sh
pnpm dsh --profile headless --dump-config
pnpm dsh --profile web --dump-config
```

## 2. 插件之间启动的先后顺序是什么？

**行序只给人读；激活序由依赖驱动。**

`boot()` 大意（`packages/boot/app-boot`）：

```text
new Context()
  → ctx.plugin(Loader)
  → prepare(hostCtx)          # ★ 任意 YAML 行之前：cmdlineArgs / appExit / appReady
  → Include 叠好的 entry 列表
  → 各 entry 并发 mount
  → loader.await()
  → assertEntriesActivated()  # 仍 PENDING / FAILED → 启动失败
```

| 规则 | 含义 |
|---|---|
| 同层 peer **并发**挂载 | 不是「上一行跑完才跑下一行」 |
| `inject: [llm]` 等 | 等 `ctx.llm`（或其它声明服务）出现才激活 |
| 服务一直缺 | fiber 停在 PENDING；审计会点名「waiting for …」 |
| `!!js` 配置 | 在声明的 inject 激活之后再求值（懒解析） |

Web 上在大量 base 并发行之外，还有一条**显式可用性链**（仍不是文件行序）：

```text
cmdlineArgs
  → web-startup
  → webserver.listen
  → web-runtime
  → connection /api …
旁路并发：llm · sessions · agent · agent-loop · agent-presets …
```

纪律（与 [010](./010-Host端内部启动顺序.md) 相同）：

1. **YAML 行序 ≠ 启动序**
2. **`webserver.listen` 可早于产品就绪**（套接字先开，`/api` 稍后齐）
3. **preset 子树晚于 Host `appReady`**

## 3. 插件启动后，是否都通过事件监听处理任务？

**不是。** 运行时是混合模型：

| 模式 | 干什么 | 典型例子 |
|---|---|---|
| **服务方法**（主干） | 直接做事 | `agent.followup()`、`ctx.llm.stream()`、`ctx.tools.execute()`、`ctx.sessions.open()` |
| **`ctx.on` + `ctx.effect()`** | 可卸载的注册 / 旁路观察 | 工具 schema、prompt 段、适配器 |
| **`ctx.emit`** | fire-and-forget 观察 | 不 await 的广播 |
| **`ctx.waterfall`** | 可拦截链（**必须 `next()`**） | `agent/pre-step`、`agent/request`、`llm/stream`、`tools/pre-execute`… |
| **`serial` / `bail` / `parallel`** | 有序决策、首否决、并行 | 如 `agent/turn-stopping`（serial，无 `next()`） |
| **Typert Remote** | Host ↔ 浏览器 RPC / 流 | `Session.prompt` → `/api/...` |
| **Session 日志 + `session/event`** | 持久事实与 UI 跟流 | `turn/start`、`assistant/message` |

实践原则（[`docs/cordis-primer.md`](../docs/cordis-primer.md)）：

> **拦截 / 策略用事件；直接能力用服务方法。**

插件 `apply` 里常见动作是：用 `ctx.effect()` 注册工具或监听，然后**等别人调用服务**——不是「自己订阅一条总线才算活着」。

三类 Cordis / 产品事件域（[`docs/architecture.md`](../docs/architecture.md)）：

| 域 | 角色 |
|---|---|
| **Session 事件** | 追加写日志，再经 `session/event` 广播——权威时间线 |
| **Agent 事件**（`agent/*`） | 带着活的 `Agent`：inbox、step、status、request… |
| **Capability 事件**（`tools/*`、`fs/*`、`llm/*`…） | 挂在能力缝上的策略与适配 |

## 4. 事件触发的流程是什么？

先分清两类，勿混：

| 类型 | 是否进 Session JSONL | 作用 |
|---|---|---|
| **SessionEventMap** | **是** | UI、回放、fork、`deriveMessages`；**模型可见 ⟺ 可从日志重建** |
| **Cordis 事件**（`agent/*`、`tools/*`、`llm/*`…） | 多数**否** | 进程内扩展点；改请求、拦工具、换适配器 |

### 4.1 一次 Web 用户说话（端到端）

```text
[浏览器] Session.prompt("hi")
    │  Typert Remote → POST /api/session/prompt
    ▼
[Host] SessionController → Commands.prompt
    │  agent.followup(UserMessage)     ← 服务调用，不是 Session 事件
    ▼
[agent-loop] inbox → wakeDriver → turn()
    │  session.append('turn/start')    ← Session 事件
    ▼
preStep:
    │  claim inbox
    │  systemPrompt.assemble()         ← 服务
    │  waterfall('agent/pre-step')     ← Cordis（可改写 / 拒绝）
    │  append step/start、user/message ← 通常先于模型调用落盘
    ▼
step:
    │  deriveMessages → buildRequest
    │  waterfall('agent/request')
    │  llm.stream → waterfall('llm/stream') → 提供方 HTTP
    │  emit agent/assistant-stream*    ← 实时跟流（常不落盘为 chunk）
    │  append assistant/message
    │  若有工具：
    │    tool/call*
    │      → tools/pre-execute → tools/execute → tools/post-execute
    │      → tool/result*
    │  append step/end
    ▼
serial agent/turn-stopping
    │  append turn/end
    │  session/event 广播
    ▼
[浏览器] WS follow → Conversation / 聊天气泡
```

跟读源码入口：

| 步 | 位置 |
|---|---|
| Remote `prompt` | `packages/api/session-controller`（client + Host commands） |
| `followup` / turn / step | `packages/core/agent-loop` |
| 组 prompt | `packages/core/system-prompt` |
| 模型流 | `packages/llm/llm` + `llm-deepseek` 等适配器 |
| UI 跟流 | `packages/client/connection` + `ui-chat` / `ui-conversation` |

更细的「说一句 hi」见 [001](./001-一次hi对话的源码之旅.md)；循环相位见 [005](./005-解剖AgentLoop.md)。

### 4.2 Architecture 上的 Turn 骨架

```text
turn/start
  → agent/pre-step
     step/start → user/message
     agent/request → llm/stream → agent/assistant-stream…
     tool/call* → tools/pre-execute → tools/execute → tools/post-execute → tool/result*
     step/end
  → agent/turn-stopping
turn/end
```

Waterfall 听众**必须调用 `next()`** 才会把链交给下游；直接 `return` 等于短路（见 cordis-primer waterfall 语义）。

### 4.3 Preset 在这条链上的位置

上述 turn 跑在 Host 已挂好的 `agent-loop` / `llm` / `sessions` 之上。
**工具 schema、persona、部分 skill** 来自该会话 bind 的 preset standing mount——在首个会话 RPC 触发 `ensureStanding` 之后才齐，**不在** Host boot 窗口里（见 [010 §6](./010-Host端内部启动顺序.md)）。

## 5. 和「全事件驱动」说法的对照

| 说法 | 更准确的说法 |
|---|---|
| 启动后插件互相只靠事件 | 先靠 **服务注入与方法调用** 组成能力；事件挂在缝上做策略 |
| 用户输入变成一条 bus 消息 | Web 上是 **Remote RPC** 进 `followup`；再由 loop **写 Session 事件** |
| UI 只听 Cordis `emit` | UI 主路径听 **Session 投影 / follow**（日志派生），辅以 live stream 帧 |
| 改行为就改 agent-loop | 优先挂 `agent/*` / `tools/*` / prompt 段等扩展点；改 loop 须同步架构文档 |
