## 1. 一图总览

```text
[首次搭建]
  pnpm install → typecheck 绿
       │
       ▼
[开分支 / 改代码]
  packages|apps|docs|scripts|snapshots|notes …
       │
       ├─ 非琐碎决策 → 同 PR 写/更新 Agent Note
       ├─ 包公开行为 → README / JSDoc 跟着改
       ├─ 模型或产品可见输出 → 录制会话 snapshot（必要时双 SDK）
       │
       ▼
[本地证据]  ← 只跑「本次 diff 会砸到」的最小集合
  单元 / coverage 局部 / snapshot / doc-sync / build+hygiene …
       │
       ▼
[git commit]  → lefthook pre-commit（staged 范围：lint 修复、空白、vendor 清单、i18n pairing）
       │
       ▼
[git push]    → lefthook pre-push（增量 typecheck）
       │
       ▼
[开/更 PR]    → 一个 kind/* + 至少一个 area/*；Issue 用 native Issue Type
       │
       ├─ 独立 PR：merge-forward 或 rebase 均可
       └─ 依赖链：GitHub native stack（gh stack）；合入走 gh stack merge
       │
       ▼
[CI]  keyless 全量门禁 + 平台矩阵；有钥匙的 e2e 另跑
       │
       ▼
[合入主干]
```

三句纪律（后面展开）：

1. **钩子故意很窄**——不替你跑测试 / 文档 / 构建；相关检查要自己选一次。
2. **本地不全量复刻 CI**——CI 拥有覆盖率门禁与 Node 矩阵；本地用最小证据。
3. **模型可见 ⟺ 可从 Session 日志重建**——可见输入变了，就要有对应 session 事件与（通常）snapshot。

## 2. 首次搭建（一次性）

前置：Node `^22.19 || >=24`（CI 还覆盖 26）、Corepack 启用的 `pnpm@11.7.0`、Git ≥ 2.26。可选：`DEEPSEEK_API_KEY`（真 API e2e / demo）。

```sh
pnpm install          # 顺带装 worktree 本地 Lefthook + 双语 pairing merge driver
pnpm run typecheck    # 绿 = 搭建完成
```

`postinstall` 若被跳过，补跑：`node scripts/install-lefthook.mjs`。
根目录 `.env` 可放 key；**永不提交**。

需要跑依赖 `lib/` 的检查或演示前，先：

```sh
pnpm run build
```

常用演示（需 key + 通常先 build）：

```sh
pnpm dsh --profile headless "task"
pnpm dsh web
pnpm run demo:ptc -- "task"
```

## 3. 日常改动：按「表面」选证据

没有统一的「推送前全家桶」。[`dsh-pre-push-checks`](../.agents/skills/dsh-pre-push-checks/SKILL.md) 的规则是：**对照即将出去的 diff，跑最小会失败的那一组**。

| 改动表面 | 典型本地证据 |
|---|---|
| 包/脚本行为 | 所属 Vitest 文件或 `-t` 过滤；共享契约变了再扩邻包 |
| `packages/*/*/src` 覆盖相关 | 聚焦测试 + `--coverage.include` 指到受影响源文件（CI 门禁是全仓 per-file 100%） |
| 文档 / Agent Note / 目录 | `pnpm run doc-sync`；文档工作流要求时再全量 lint |
| 模型、CLI、终端、协议可见输出 | 对应 keyless `test:snapshot`（或 owner-local `test:expected` / `test:web`） |
| 清单、exports、构建配置、产物路径 | `pnpm run build` + 相关 hygiene / built smoke |
| 真模型 / 真 provider | 有钥匙时跑对应 `test:e2e`；无钥匙 suite 自跳过 |
| 仓库级不可切分的大改 | 才考虑接近全量；或用户明确要求 `check:all` |

常用命令速查（完整列表以根 `AGENTS.md` / `package.json` 为准）：

```sh
pnpm run test              # 单元
pnpm run test:coverage     # CI 覆盖率门禁（别默认当本地基线）
pnpm run test:e2e          # 真 API；无 key 自跳过
pnpm run test:expected     # 无钥匙、非录制会话的期望输出
pnpm run test:snapshot     # 录制会话回放；-t <name> 过滤
pnpm run test:snapshot:record   # 重录（需 key）；审 diff
pnpm run typecheck
pnpm run lint
pnpm run build
pnpm run hygiene           # 需已有 build 产物
pnpm run doc-sync          # 文档门禁聚合
pnpm run test:docs         # 快速文档检查
pnpm run check:all         # 可选：本地综合门禁，与钩子无关
```

**不要**在即将 push 时再手跑一遍 typecheck 只为了重复 pre-push 钩子。
**不要**因为「马上要提交」就重复已绿的同一检查。

### 测试分层（记名字）

| 层 | 命令 | 证明什么 |
|---|---|---|
| Unit | `test` | 包内行为、契约回归、HMR dispose |
| Coverage | `test:coverage` | `packages/*/*/src` per-file 100%（CI 门禁） |
| Snapshot | `test:snapshot` | 装好的 profile 上，录制 Session 的产品可见回放 |
| Expected | `test:expected` | 无 Session 往返的 CLI/进程期望 |
| Web | `test:web` | Chromium；Linux PR 门禁之一 |
| E2E | `test:e2e` | 真 provider；有钥匙才有意义 |

策略要点：

- 非琐碎的**模型 / 协议 / 人眼可见**改动，同 PR 更新 keyless 录制会话；单元与 mock 不能代替装好的 transcript。
- Agent-loop / session 生命周期 / `SessionEventMap` 改动要同时更新 **TS + Python** SDK 期望输出。
- Mock 只挡贵且不确定的边界（LLM、网络、时钟）；下游尽量真实现。
- e2e 断言「外部世界」（文件、进程退出），不要只扫 agent 自述文本。

细节与放置规则：[`docs/testing.md`](../docs/testing.md)、[`snapshots/AGENTS.md`](../snapshots/AGENTS.md)。

## 4. Git 钩子 vs 你手动跑的检查

Lefthook（worktree 本地）是**快速卡口**，不是全量 CI：

| 钩子 | 做什么 | 故意不做 |
|---|---|---|
| `pre-commit` | staged：pairing 校验、Oxlint（可修复一次）、THIRD_PARTY 再生、空白、`vendor` 清单与源同改 | 测试、snapshot、doc-sync、build、hygiene |
| `pre-merge-commit` | 合并前提 index 上的 pairing 检查 | 同上 |
| `pre-push` | `pnpm run typecheck`（含 Host Typert 契约再生后再 Client 检查） | 同上 |

改 `vendor/*/src` 必须同 stage 更新 `vendor/README.md` 清单。

双语文档：owner 文件 + `.i18n.yaml` pairing；合并冲突走配对 merge driver / `pnpm run resolve-translation-pairing-conflicts`。日常翻译流程见 [`docs/i18n`](../docs/i18n/README.md)；**不要**默认代用户跑 `dsh-translate-docs`（需显式调用）。

## 5. 文档与决策记录（和代码同 PR）

```text
改行为 / 契约 / 结构 / 流程 / 测试策略 / 持久化或线协议
        │
        ▼
  同 PR：Agent Note（proposed|implemented|rejected × class）
        │
        ├─ 包对外语义 → 包 README（含 Known Limitations 等门禁段）
        ├─ 类型目录 → docs/subsystems 对应页 + type-equiv 如需
        └─ 架构扩展点 / agent-loop → docs/architecture.md（改 loop 必更）
```

| 产物 | 角色 |
|---|---|
| Agent Note | **为什么**、放弃了什么、要验什么；`implemented/` 用现在时描述已落地事实 |
| Package README | 包契约：配置、语义、限制、扩展点 |
| `docs/` | 教程 / 参考 / cookbook；一事实一归处 |
| `wiki/`（本目录） | 专题跟读稿；**不进**官方 doc 门禁 |

琐碎机械改动可免 Note；否则「非琐碎改动必须同 PR 带 Note」。
归档 Note 冻结，不可当现行权威。

Cookbook 起步：[`adding-a-package`](../docs/cookbook/adding-a-package.md)、[`adding-a-tool`](../docs/cookbook/adding-a-tool.md) 等。

## 6. 分支、PR、栈与合入

### PR 元数据

- 恰好一个 `kind/*`：`feature` | `bug-fix` | `doc` | `testing` | `cleanup` | `dependency`
- 至少一个实质触及的 `area/*`（可多个；不要叠「总称 + 其子项」重复）
- Issue 用 GitHub **Issue Type**，不用 `kind/*`

### 历史策略

- 独立 PR 与官方 stack 层：允许 **merge-forward** 或 **rebase**（含 review 后）
- 改写远程：`--force-with-lease`（或 `gh stack` 自带租约）；**禁止**裸 `--force`
- 依赖链（≥2 个同仓 PR）：落地前挂 **GitHub native stack**；合入用 `gh stack merge`，不要手搓逐个 `gh pr merge` + 改 base
- `gh stack sync` 会「拉基线 → 级联 rebase → 推送」一次做完：推完后**立刻**按层补跑相关证据，未绿勿合

栈上修 review：修在**引入该问题的层**，再按 cookbook 传播。见 [`responding-to-pr-review-on-a-stack`](../docs/cookbook/responding-to-pr-review-on-a-stack.md)、[`dsh-merging-stacked-prs`](../.agents/skills/dsh-merging-stacked-prs/SKILL.md)。

### CI 心智

- Keyless workflow：按车道跑门禁；产物消费者等本车道一次 build。
- 真 API workflow：另跑 `test:e2e`。
- 本地相关证据绿了再 push；冲突态 PR 可能根本不触发 checks——先解决冲突，不要靠空 commit「踢」CI。

## 7. 写代码时的几条硬约定（流程向）

这些不是架构细节，但决定「改完能不能顺利过门禁」：

| 约定 | 含义 |
|---|---|
| 一切皆插件 | 新行为优先挂扩展点；动 `agent-loop` 必须同步架构文档 |
| Capability Seam 三角色 | Service Definition / Provider / Consumer 成套，不单挂一端 |
| 注册即 effect | `ctx.effect` / `ctx.on`；`register()` 返回 disposer |
| 配置可调 | 部署可变项进插件 `Config`（cordis.yml），禁止插件里写死可调参 |
| 品牌 ID | 跨边界不透明 id 用 `Branded<>`，不用裸 `string` |
| Host / Client 两套 program | 普通包只进一侧 aggregate；源平面测 `src`，产物平面显式消费 `lib/` |
| 发布 Session 迁移 | 只允许相邻世代共存式演进；不覆盖、不删已提交世代 |
| 应用启动 | 支持的 Node 应用只经 `dsh` profile；禁止包 bin / demo / 公共 SDK argv 逃生舱当正式启动面 |

完整站立规则：根 [`AGENTS.md`](../AGENTS.md)。改生命周期 / 并发 / 子进程前读 [`docs/defensive-patterns.md`](../docs/defensive-patterns.md)。

## 8. 推荐工作顺序（清单）

一次功能或修 bug，可按此核对：

1. **读**相关 `docs/architecture.md` 段 + 包 README + 是否已有 Agent Note
2. **改**最小表面；契约变更更新所有消费者（API 预稳定）
3. **测**所属单元；触及可见输出则 snapshot / expected；覆盖相关则局部 coverage
4. **记** Agent Note + README/JSDoc/子系统页（按触及面）
5. **检** `doc-sync`（若动了文档体系）、必要的 `build`/`hygiene`
6. **交** commit（看 pre-commit 是否改写了 staged 文件）
7. **推**（pre-push typecheck）；`gh pr checks` 盯 CI
8. **合** 独立 PR 或 `gh stack merge`；rebase/sync 后重审评论锚点与 checks

沙箱若挡住 `gh` / `pnpm` / 网络 / 嵌套 sandbox：在有证据后用**最窄**权限重试同一命令；不要用绕过掩盖真实测试失败。
