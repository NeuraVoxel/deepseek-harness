# 001 · 一次 hi 对话的源码之旅

> DeepSeek Harness 源码专题 · 第 1 篇
> 先读流程地图：[000 · 当前项目开发流程](./000-当前项目开发流程.md)
> 入口：Web UI · 主线：Harness 如何组织对大模型的一次调用

你在浏览器里敲下 `hi`，点发送，几秒后聊天气泡里出现回复。
中间发生了什么？

本文跟读 **最短路径**：没有工具调用、没有多轮打断，只有一条用户消息、一次模型请求、一条助手回复。
Web UI 是入口；讲清楚之后，重点落在 Harness **内部如何组织 turn / step，并真正把请求打到大模型**。

可对照命令：

```sh
pnpm dsh web
# 或：npx @deepseek-ai/dsh web
```

打开页面后新建 Session，输入 `hi` 发送即可。下文按源码顺序拆开这一条链路。

---

## 全链路一图

```text
[浏览器 Composer]
    │  Session.prompt (queue)
    ▼
[HTTP POST /api/session/prompt]
    │  SessionController → Commands.prompt
    ▼
[Agent.followup("hi")]
    │  Inbox → wakeDriver → kick → turn
    ▼
[preStep]
    │  claim inbox · systemPrompt.assemble · agent/pre-step
    │  append user/message
    ▼
[step]
    │  deriveMessages · buildRequest · llm.stream
    │  DeepSeek adapter → POST …/chat/completions
    ▼
[assistant/message 落盘]
    │  turn/end
    ▼
[WS session/follow]
    │  Client Session → ui-chat 气泡
    ▼
[你看到回复]
```

记住三个名字：

| 概念 | 含义 |
|---|---|
| **Session** | 追加写的事件日志；模型看到的历史从这里投影出来 |
| **Agent** | 驱动一次 Session 的运行时（默认实现是 `ReactLoopAgent`） |
| **Turn / Step** | Turn = 零或多步；Step = 一次模型请求 + 它触发的工具 |

`hi` 这条最短路径里：**1 个 turn、1 个 step、0 次工具调用**。

---

## 第 1 站 · `dsh web` 起了什么（短）

CLI 入口在 `apps/cli/src/bin.ts`：`dsh web` 被解析成 `--profile web`，再进入 `runProfile`。

`web` profile 叠两层 bundle：

1. **`@deepseek-ai/dsh-base`** — 模型适配器、agent-loop、tools、session 持久化等共享能力
2. **`@deepseek-ai/dsh-web-app`** — 在 base 之上挂 Host（HTTP/WS、Session API）和前端静态资源

浏览器里跑的是 Client 插件树（composer、chat、connection）；Node 进程里跑的是 Host + 同一棵 Cordis 服务树里的 agent-loop / llm。

对本专题：只要知道 **「UI 在浏览器，真正调模型的是 Host 进程里的 Agent」** 即可。

---

## 第 2 站 · 输入框到 `followup`（入口）

### 浏览器侧

输入框与提交机在 Client 对话层：

- UI：`packages/client/ui-conversation/.../InputBar.tsx`
- 提交状态机：`SubmitMachine`（`.../input/machine.ts`）
- 会话发送：`ConversationService.sendSession` → `Session.prompt(content, mode)`

普通空闲发送时，`mode` 是 `'queue'`（跑着的时候「插话」才是 `'steer'`）。

`Session.prompt`（`packages/api/session-controller/src/client/sessions/session.ts`）通过 Connection 发一元 RPC：

```text
POST /api/session/prompt
body ≈ { type: 'client-request', method: 'session/prompt', sessionId, mode, content: [{ type: 'text', text: 'hi' }], ... }
```

流式回推走另一条路：WebSocket 多路复用（例如 `/api/remote.mux` 上的 `session/follow`）。
**发消息是 HTTP；看回复是 WS。**

### Host 侧

Gateway 把请求落到 `SessionController` → `Commands.prompt`
（`packages/api/session-controller/src/commands.ts`）：

```ts
const message: UserMessage = createUserMessage({ content, source })
if (request.mode === 'steer') agent.steer(message)
else agent.followup(message)
```

对 `hi`：构造一条 `UserMessage`，调用 **`agent.followup(message)`**。
从这里开始，和 headless / SDK 共用同一套 Agent 驱动。

## 第 3 站 · Inbox 醒来，打开 turn（主）

默认 Agent 驱动是 `ReactLoopAgent`（`packages/core/agent-loop/src/agent.ts`）。

```ts
followup(input: UserMessage): void {
  this.send(input, 'next-turn', true)
}

send(message, target, wakeup): void {
  this.inbox.splice(/* … */, [message])
  if (wakeup) this.wakeDriver(/* … */)
}
```

含义很直白：

1. 把 `hi` 塞进 **Inbox**（目标 `next-turn`：下一轮再取）
2. **叫醒** 驱动器（`wakeDriver` → `kick` → 循环 `turn()`）

`turn()` 一上来先往 Session 日志写边界事件：

```ts
this.session.append('turn/start', { turn })
```

然后进入 `preStep` →（通过后）`step/start` → 真正的模型调用 → `step/end` → `turn/end`。

Session 日志是权威时间线；后面 UI、fork、回放都从这些事件来。

---

## 第 4 站 · `preStep`：认领消息 + 组装系统提示（主）

`preStep` 做三件对「调模型」至关重要的事：

```ts
const claimed = this.inbox.claim(target, position.turn)
const assembly = await this.loopCtx.systemPrompt.assemble(assembleContextFor(this, signal))
const decision = await this.dispatch.waterfall(
  'agent/pre-step', { messages: claimed, ...position, signal },
  () => Promise.resolve({ kind: 'enter', messages: /* claimed + 可选 runtime context */ }),
)
```

| 步骤 | 作用 |
|---|---|
| `inbox.claim` | 从收件箱取出本步要进模型的用户消息（这里就是 `hi`） |
| `systemPrompt.assemble` | 收集各插件注册的 prompt 段与工具 schema |
| `agent/pre-step` waterfall | 插件可改写/拒绝本步；默认 `enter` |

通过后：

```ts
this.session.append('step/start', { turn, step })
for (const message of decision.messages) {
  this.session.append('user/message', message, { surfaceOp: 'append' })
}
```

**先落盘 `user/message`，再调模型。**
原则：**模型可见 ⟺ 已记入 Session 日志**——能重建请求，也能在 UI 里回放。

## 第 5 站 · `step`：拼请求，调用大模型（主）

`step()` 是全文重心。

### 5.1 拼出这一次 GenerateOptions

```ts
const system = renderPrompt(assembly)
const { request, preparedCall } = await this.buildRequest(
  turn, step, assembly.tools, system,
  this.session.deriveMessages(),  // ← 从日志投影出的对话历史
  startsRequestSeries, surfaceGeneration, signal,
)
```

要点：

- **`system`**：各插件贡献的系统提示渲染结果
- **`deriveMessages()`**：不是另存一份聊天数组，而是从 Session 事件投影「模型该看到的历史」
- **`buildRequest`**：经 `agent/request` waterfall 与 `llm.prepareCall`，冻结合法的 `GenerateOptions`（provider / model / messages / tools / …）

对第一次 `hi`：历史里通常只有刚写入的那条用户消息（外加系统侧上下文）。

### 5.2 真正打到模型：`llm.stream`

```ts
const stream = preparedCall?.stream(request) ?? this.loopCtx.llm.stream(request)
live.start()
for await (const chunk of stream) {
  live.push(chunk)  // 同时 emit agent/assistant-stream，给 Web 跟流
}
```

`LlmRuntime.stream`（`packages/llm/llm/src/index.ts`）再走 `llm/stream` waterfall，选中对应 **adapter**：

```ts
stream(options: GenerateOptions): AsyncIterable<StreamChunk> {
  return this.streamWithRegistration(options)
  // → waterfall('llm/stream') → adapter.stream(...)
}
```

默认 DeepSeek 适配器（`packages/llm/llm-deepseek/src/adapter.ts`）把 Harness 的 `GenerateOptions` 编成 OpenAI 兼容请求，例如：

```text
POST {baseURL}/chat/completions
```

流式 chunk 被 `AssistantStreamAttempt` 收成块；过程中 Host 发出 **`agent/assistant-stream`**，供 UI 逐字更新。

### 5.3 没有 tool 时如何结束

流正常结束且内容里没有 `tool-call`：

```ts
live.settle('assistant/message', () =>
  this.session.append('assistant/message', {
    turn, step, message, usage?, stream: live.stream,
  }, { surfaceOp: 'append' }).seq,
)
return { kind: 'completed' }
```

随后 `step/end`、`turn/end`（reason 多为 `{ kind: 'completed' }`）。
驱动器发现 Inbox 空了，回到 `idle`。

若有工具调用，会 `executeToolCalls`，再开下一步模型请求——那是后续专题；`hi` 不走这条岔路。

## 第 6 站 · 为什么 Session 日志是中枢（主）

把「调模型」和「记日志」绑在一起，是 Harness 的骨架：

| 事件 | 角色 |
|---|---|
| `turn/start` / `turn/end` | 一轮边界 |
| `step/start` / `step/end` | 一次模型调用边界 |
| `user/message` | 进入模型前的用户侧事实 |
| `assistant/message` | 成功结算的助手回复（含紧凑 stream） |
| `assistant/attempt` | 失败/重试/取消等未进入模型历史的尝试 |

下游都读同一份日志：

- **下一轮请求**：`deriveMessages()`
- **Web 时间线**：`session/event` + 跟流
- **持久化 / 导出 / fork**：同一套 Session 事件

所以：扩展「模型能看见的新输入」，通常要新增 Session 事件类型，而不是只改内存里的某个数组。

---

## 第 7 站 · 回到聊天气泡（短）

Host 的 `History.follow`（`packages/api/session-controller/src/history.ts`）订阅：

- `session/event` — 耐久事件（含最终 `assistant/message`）
- `agent/assistant-stream` — 过程中的流式帧

打成 `SessionFollowFrame`，经 WS 推到浏览器。
Client 的 Session 对象折叠这些帧；`ui-chat` 用 Conversation Node 把助手步渲染成气泡。

你感知到的「打字机效果」，来自跟流帧；刷新后仍能看见完整回复，来自已落盘的 `assistant/message`。

---

## 小结：`hi` 在 Harness 里走了哪几步

1. **UI 入口**：Composer → `Session.prompt` → HTTP → `Commands.prompt` → `agent.followup`
2. **调度**：Inbox → `wakeDriver` → `turn` / `step`
3. **组织请求（核心）**：claim → `systemPrompt.assemble` → 落盘 `user/message` → `deriveMessages` + `buildRequest`
4. **调用模型**：`ctx.llm.stream` → DeepSeek adapter → `/chat/completions`
5. **结算**：`assistant/message` → `turn/end`
6. **回显**：WS `session/follow` → 聊天气泡

一句话：

> Web 只负责把 `hi` 送到 Agent；
> **真正「组织调用大模型」的，是 agent-loop 在 Session 日志边界上组装请求，再经 `ctx.llm` 交给适配器。**
